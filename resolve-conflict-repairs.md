## Goal

Make every conflict between two clones end in a stored record both sides were reviewed for: git merges the ledgers, sync_ledger hands each conflicted record's versions to the model to review and recommend, and resolve_conflict stores the composed record without losing remote decisions or session entries, including when the ledgers share no history.

## Where things stand

Released as 11.0.0 (main at 7b6cf210, installed at user scope, pending a restart). git merges the ledger with git merge-tree; every conflicted path must be one side's file whole, and an entry that is not a regular file is refused; the conflict reply gives logbook://conflict addresses, a clipped change list, and says the names and lists are a teammate's data. resolve_conflict takes each conflicted file whole, checks only the stored shape and that ids match the path, refuses a conflict that changed locally since the sync, and commits onto git's merged tree so the shared copy's other work survives. ## Decisions in force

- D1 Merge ledgers with git and review each conflicted record whole, instead of Logbook's field-by-field merge: Merge with git. Confirmed by the human with three adjustments. (1) Records are single-line JSON (src/store/write-path.ts:56), so git reports any concurrent edit to the same thread as a whole-file conflict. That is more conflicts than today, accepted because concurrent work on one thread is not expected and review covers the whole record anyway. (2) resolve_conflict takes the record as it should now read, composed from both versions, not a local or remote winner per field. (3) Logbook still checks that a stored record fits the stored shape, because an unreadable record is a storage failure. It drops rules that judge content, so the PR #258 next-step pair rule has nothing left to guard. Defects 1 and 2 are removed at the root; the no-shared-history case uses merge-tree --allow-unrelated-histories.
- D2 Q1: sync no longer refuses a remote record this version cannot parse: Stop refusing, as recommended; ruled by the human. git merges bytes without parsing, and item 8 of the deferred cap items already quarantines one unreadable record without breaking the rest.
- D3 Q2: sync no longer refuses when this clone holds a record it cannot read: Stop refusing, as recommended; ruled by the human. The protection existed only because the field merge decided records from their parsed form; git merges bytes.
- D4 Q3: the conflict reply lists which JSON paths differ, as a reading aid only: List the differing JSON paths, as recommended; ruled by the human. It is display code that makes review more accurate, not merge logic, and it decides nothing.
- D5 Q4: conflict versions are read through logbook://conflict/{blob_id}, not inlined: Resource addresses, as recommended; ruled by the human. Keeps the reply small whatever the size or number of conflicted records.
- D6 Q5: a conflicted file outside the four record directories is resolved as text and stored as given: Accept a string and store it as given, as recommended; ruled by the human. Logbook never checked those files' shape, so there is nothing to check.
- D7 Q6: below git 2.38.0 only the merge path is refused, naming both versions: Refuse only the merge path, as recommended; ruled by the human. Fast-forward, push and nothing-to-do need no merge-tree and keep working.
- D8 Q7: review guidance lives in the conflict reply only, not in a plugin skill: Reply only, as recommended; ruled by the human. The reply reaches the model at the moment of the conflict without a skill having to load.
- D9 Q8: a merged record that is not one side's file whole is treated as a conflict: The one-side-whole check alone, as recommended; ruled by the human. It covers every source, custom drivers included, on every git version; the flags cover only some sources and may raise the floor.
- D10 resolve_conflict escapes a composed record by each field's schema class: Walk the schema by class, in src/schema/escape-record.ts (escapeStoredRecord). On every schema-valid record it escapes exactly the tool-escaped set: the only content or pointer fields tools leave unescaped are slug and decision commit, whose patterns (SLUG_PATTERN, SHA_PATTERN) admit no character escapeStored changes. A new content field is escaped on resolution without anyone remembering to add it. test/unit/escape-record.test.ts spells out the tool-escaped set per kind as a literal expectation, so class metadata drifting from tool behaviour turns it red; mutations 'content only' and 'escape every string' each turned it red at the time of recording.
- D11 A conflicted path is a record only when it matches a record address; any other path is settled as text: Decide by the full address grammar, in recordAddressOf in src/server/tools/resolve_conflict.ts. Every file Logbook itself writes is a record address and is shape-checked; a file no tool writes can always be settled. The published path pattern is kept loose (no leading slash, no NUL or line break) for the same reason, so no conflicted file is left unsettleable.
- D12 Relabel the three no-literal-identifiers control candidates instead of deleting them: Change the label to unit/records.test.ts. The controls prove the census halts on a literal inside an assertion, a binding referenced only inside assertions, and an unresolvable binding shape; none of that depends on field-merge.ts, so deleting them would lose coverage for no reason. Noted in spec section 5.
- D13 resolve_conflict's path cap is 4096, Linux PATH_MAX: 4096, committed in 452a62d8 with a chosen-basis row in docs/registers/size-limits.json. It is far above the longest record address (67 characters) and covers any path the systems Logbook runs on can hold.
- D14 Logbook handles ordinary conflicts and does not police a hostile ledger push: Defer the adversarial cases. The human ruled: 'To clarify, two people working on the SAME Logbook thread is NOT a primary use case for Logbook. Logbook should be able to handle the most basic conflicts and cases. It should NOT police force-push or similar overrides. That is NOT it's job.' So this branch fixes what an honest ledger can reach plus anything costing a few lines that removes a class of nonsense Logbook never writes (entries that are not regular files), and records the rest as risks: unsettleable exotic paths, the 200-resolution cap with reply size, raw-path traversal that git already refuses, unescaped content at a hand-placed record path, and non-UTF-8 paths. Separately the human chose to extend the not-taken-whole check from record directories to every conflicted path.

## Open risks

- R1 A whole composed record sent as one resolve_conflict argument may be cut short above the plugin boundary; an earlier observation saw long ledger-tool payloads lose their tail, though a long record_decision succeeded on 2026-09-15. Bears on c3.
- R2 git older than 2.38.0 has no merge-tree --write-tree, and Ubuntu 22.04 ships 2.34.1 by default, so the merge path cannot run there. Bears on c1.
- R3 A conflicted path git allows but resolve_conflict cannot name leaves sync refusing forever: a path with a line break (the input pattern refuses it and the escaped rendering is not accepted as a name), a path over RESOLUTION_PATH_MAX, or more than 200 conflicted files at once, since a partial list is refused. Reproduced end to end for the line-break case by the step 8 security review; all of it needs a teammate force-pushing a crafted ledger, which decision 01M2KNP17Y01JRNC3ZT1302A4D rules out of scope.
- R4 The conflict reply has no total size limit, so many conflicted files or a very large record can pass the MCP output limit even with the per-entry change list clipped. The 200-resolution cap is reached only well past that point.
- R5 writeRecords writes a raw change to path.join(layout.records, relPath) with no path validation of its own; only git's own refusal of .. and .git segments in update-index and read-tree keeps a crafted path inside the records directory. A future caller passing a raw change would have no protection. The materialiser's validateEntries rules in src/store/materialise-tree.ts are the ready-made check.
- R6 Content settled at a path inside a record directory that is not a record address (for example threads/evil.json, which only a hand-made or force-pushed ledger contains) skips the stored-shape check and escapeStoredRecord, and readThreads serves every threads/*.json, so unescaped text can reach a briefing. Requiring a record there instead would make such a path unsettleable.
- R7 Git paths are decoded as UTF-8 (src/store/git.ts gitRun), so a conflicted path with non-UTF-8 bytes becomes a U+FFFD-altered path: the resolution is stored at the altered path while the original keeps git's conflict markers in the commit. Logbook writes no such path.
