Logbook, rebuilt: why the shape of the plan is the point

Reads alongside docs/specs/2026-08-22-logbook-rebuild.md — the executable definition.
This document is the explanation: what broke, why the previous repair failed, and what each decision costs.

Logbook is a plugin that remembers a software project across working sessions. It stopped being trustworthy in two specific ways, and an earlier 128,787-byte plan to fix it did not land. The rebuild is organised around removing six design decisions that produced nearly every catalogued defect, rather than fixing symptoms — and around three process rules that exist because of exactly how the last attempt failed.

Section 1What Logbook is, and what went wrong

Logbook is a plugin for Claude Code. When a working session ends it writes down what was being worked on, what was decided and why, and what the next step is. When a session starts it presents that back, so the next session begins informed instead of blank. It keeps that record inside the project's own git repository, so several people working on one project share one history.

It reaches the assistant over MCP — the Model Context Protocol, a published protocol by which a client program talks to a small server that offers it tools (things the model can call) and resources (things the model can read). Logbook's server runs as a child process and talks over stdio: plain standard input and standard output pipes. That detail is not trivia; it decides several later design choices, because a single stray character printed to standard output corrupts the channel.

Failure one: a tool that is hard to call correctly

Invoking the hand-off flow took several attempts, which the user saw as the assistant fumbling the same call repeatedly. The cause is mechanical, not stylistic. The client does not load full tool definitions at session start: it loads tool names plus a single server instructions string, and fetches a tool's full input schema only when it decides to look. If the name and the short description do not convey the shape of the data, the caller has to discover it in stages — and each stage is a visible failed call.

Failure two: a tool that loses the state it exists to keep

The second failure is more serious, because it defeats the plugin's entire purpose. Logbook tracks a thread: one line of work, carrying its goal, its completion criteria, and a running summary called the spine. A gate is supposed to notice at session end that a thread is still open and prompt for a hand-off. In practice that gate fired constantly in the session that opened a thread, and never again afterwards.

The mechanism is wrong in both directions at once, which is the tell that this is a design fault rather than a bug. Two separate things were mismatched: the gate hung off an event that fires once per turn rather than once per session, and the fact it consults — "is this thread being worked right now?" — was stored on the thread record, where nothing reliably cleared or set it. Section 4 shows how the rebuild removes both, and section 3 places them in the wider pattern.

Section 2Why the previous attempt failed

The single most important finding in this report

The 2026-08-04 hardening plan did not fail because it was too short. It is 128,787 bytes long. It failed because its premises were never checked against the code before it was approved, and because the work it authorised had no ceiling on what counted as done.

A premise here means a statement of fact about the existing code that a unit of work depends on — "this function currently does X", "this file has no caller". Those statements were written when the plan was written, and then not re-checked when each unit was picked up, sometimes weeks later. Decision record 0054 re-planned the four units of that plan that had not yet been started, checking each one's premises against the actual tree. All four returned premise_holds = false. The plan was, by then, a description of a codebase that no longer existed.

Compounding it, the work that was done ran into a review treadmill. Eighteen consecutive review rounds each found a real defect while the test suite reported 100% passing — and nine of those eighteen defects were introduced by the fix for the round before.

Two further rules come from the same post-mortem and are cheap to state. Fix what you introduce; defer what you inherit — a unit repairs the defects it creates, and files any defect it merely encounters with a named owner rather than silently absorbing it. And preserve the distinction — this project's recurring failure shape is a change that quietly collapses a distinction the previous version was carrying, four times in a single unit of work, so every change now states which distinction it preserves and which it collapses before it ships.

Section 3The six architectural root causes

Six design decisions produced nearly every catalogued defect. This is the spine of the rebuild: each one is removed, not guarded. The governing rule is that robustness and simplicity are joint criteria rather than a trade — a design that needs a fourth special case to stay correct is the wrong design, and where a defect class can be deleted rather than defended against, it is deleted.

E1 · storage
Git plumbing used as the engine, not the transport

A worktree is a developer's checked-out copy of a repository. It has no concurrency model, so using one as a database gives you recursive delete as a state transition, a strategy flag as a conflict resolver, and a directory scan as a way to allocate numbers.

produced worktree destruction, number collision, silent merge loss, two diverged stores, a 50-subprocess session start, no durability barrier.

Removed byNo worktree at all. Records live in a plain directory and reach a git ref through plumbing commands, with every ref move a compare-and-swap and every merge performed record by record.
E2 · hooks
Events chosen by availability, not by meaning

A hook is a small program the client runs when something happens. Six of roughly thirty-one available events are wired, and two notifications sit on per-turn and per-tool-call events while reporting per-session conditions.

produced the hand-off nag every turn, a compaction nudge on every tool call, publication logic inverted, a session-start hook that ignores its own stated cause.

Removed byState the condition and its natural cadence first; then bind the event whose firing matches it. Where no event matches, add an explicit latch.
E3 · ownership
Skills own rules the server should own

A skill is a Markdown file of instructions. The lifecycle's most important transition was enforced by a Markdown list of permitted tools: the resume skill was allowed only four read-side tools, so the transition it needed was not merely unused, it was forbidden.

produced the entire resume defect, and the gaps in the tool surface. Editing a Markdown file silently disabled resume, and no test could catch it, because no code was wrong.

Removed byIf a rule is load-bearing, the server performs it. Skills orchestrate and hold no rules.
E4 · errors
Errors converted into absence

Nine bare catch blocks, twenty-two unchecked git calls, and a helper that maps both a non-zero exit code and a parse failure to the same empty value. The signature symptom: an unset environment variable renders to the user as "no resumable threads" — a confident positive claim about a store that was never read.

produced invisible misconfiguration, git failures that silently downgrade the driver, a guard that degrades when it cannot resolve a path.

Removed byAbsence and failure become different values, structurally. A read that failed is an error; only a read that succeeded and found nothing is empty.
E5 · records
Records written before anyone asked who reads them

248 KB of session logs and a directory of compaction checkpoints, neither of which had a reader anywhere in the system.

produced two write-only stores — pure cost, zero return.

Removed byEvery record type names its reader in the SPEC. Session logs get a real reader by being published as addressable resources; the checkpoint directory and its hook are deleted.
E6 · truth
Truth declared twice, reconciled never

The record shape was declared in two places, validated on write but not on read, and refusal messages were re-derived by hand rather than projected from the schema that already knew the answer.

produced validation drift, unhelpful refusals, test results that depend on the developer's environment.

Removed byOne declaration per record type emits four things: the type, the runtime validator, the wire schema sent to the client, and the text of a refusal when validation fails.
The rule underneath all six

What the server enforces is robust. What depends on the agent remembering is where the ledger rots. If a property matters, the server refuses the write that violates it. A rule stated in a skill file, a description, or a specification is not a mechanism.

Five decisions do most of the shaping. Each buys something specific and forecloses something specific; none is free.

Why there is no worktree, in evidence

The case is not theoretical. In the current build, the code that provisions the checkout deletes the live directory even when it failed to acquire the lock — reproduced by waiting out the full 10.2-second timeout, failing to acquire, and deleting a second session's uncommitted file anyway. A lock older than ten seconds is declared stale and removed, so a slow holder is robbed; that was reproduced in 0.6 seconds. The lock covers provisioning only and releases long before the writes it should protect. Two worktrees for this repository are registered right now, and because both use the same basename git had to disambiguate one of them. The command that removes a worktree appears nowhere in the source: the lifecycle is create-and-abandon.

The reading that matters

None of that is a locking bug to fix. It is a checkout that should not exist.

The write path

Some vocabulary first. Git's plumbing is its low-level command set — the commands that manipulate objects and refs directly, beneath the everyday commands like commit and checkout. A ref is a named pointer to a commit; branches are refs that live under refs/heads/. An orphan ref is one whose history is unrelated to the project's own branches. Compare-and-swap is the discipline of saying "move this pointer from the old value I read to this new value, and fail if it is no longer the old value" — which is what makes two processes unable to silently clobber each other.

The merge decision

Two people can work on the same project offline and each record something. When they reconnect, both sets of changes must survive. Today everything except session logs falls through to a merge that takes the remote side wholesale, reports success with exit code 0, and then force-pushes — silently discarding a teammate's thread record.

Three states, and two things that are not states

A thread stores one of three states. Two facts that used to be states are now derived or field-borne, and that is the direct repair of the section 1 defect.

Two more choices worth naming

Resuming is one call, and parking is one call. Today resuming is three chained calls — refresh the index, reconcile, render the briefing — which is exactly what the user saw collapse into "Called 3 times". Chained tools are a named anti-pattern: if a human engineer cannot say which tool to call, a model cannot either. resume_thread reconciles, writes the pointer and returns the rendered briefing in one call; park_thread writes the session log, refreshes the spine and releases the pointer in one call.

Write tools report what changed, not what the record now is. A call that removes two recorded decisions returns their ids. That closes the class of bug where deletion, no-op and success are indistinguishable, and it collapses one measured return from 6,269 bytes to a fraction of that. In the same spirit, a refusal is generated from the schema rather than hand-written, and states four things: which field was wrong, what is accepted, a valid example, and whether a retry can succeed. During the authoring of the SPEC a current refusal was reproduced that named the field and the limit but left its example field null, so the caller could not tell which of several values was too long.

Section 5How it will be built

Twelve units. Each is independently shippable and merges green — which is unusually cheap here, because the rebuild grows as a parallel tree and nothing the installed plugin loads is touched until the final cutover unit.

Five obligations every unit carries, without exception
  1. Re-verify its premises against the tree before code is written, and record the result.
  2. Declare its acceptance criteria before starting, and treat them as a ceiling.
  3. Ship at least one assertion proven red on the parent commit.
  4. Ship an inertness mutation: revert what the unit added, and the assertion must turn red. A test that survives that is not testing the change.
  5. Fix what it introduces; file what it inherits, with a named owner.

Two supporting choices in the build itself

TypeScript, decided by distribution. The plugin manifest has no platform, operating-system or architecture field, so a compiled language would have to ship several binaries plus a shell selector — and a shell selector breaks on Windows. TypeScript ships one platform-independent artifact. Development needs no build step, because Node runs TypeScript directly; but type stripping performs no type checking, so a type check runs before every commit and the released artifact is compiled.

Guard rails that exist from the first commit, rather than being added after the first incident: a lint rule forbidding any write to standard output in server code (the transport is standard output, which makes this the highest-value five minutes in the project), the pre-commit type check, the schema-description census, and the escaping census. The MCP Inspector — an independent client implementation, currently absent from the repository entirely — becomes the development loop and one smoke step in CI, with its version pinned exactly because version 2 was a full rewrite and nearly all published guidance describes version 1.

Section 6What green will prove — and what it will not

If a green pipeline does not prove the plugin works when used live, it is a bad test and a waste of time.

The bar the rebuild's test suite is held to

That bar is achievable for most of this system and not all of it. The end of this section names the gap plainly, because pretending otherwise is the specific dishonesty the section exists to prevent.

The current suite, measured

The problem is not the number of test files. It is where the weight sits. A fixture is the scaffolding a test stands up before it runs; a hand-built context is a fake version of the data a real caller would have sent.

Worse than a weak assertion

A fixture that builds a non-git directory when production is git-backed does not merely test weakly — it quietly builds a different system than the one that ships. With the rebuild git-only, that fixture defect would be fatal. Proof that assertions can be entirely inert: deleting three lines of production code left the suite at 971 of 971 passing.

Mutation testing, named there, means deliberately introducing small changes into the production code and checking that some test turns red. It measures whether the assertions actually assert. It gates the diff with an explicit break threshold — never 100%, because some mutants are provably equivalent to the original and no test can distinguish them. Coverage is reported and never gated; it is read for what is not covered.

The worked example: two teammates, offline

This is the acceptance test for team sync and the model for every honest test in the suite. A real bare repository as the shared remote; two real clones; two real server processes, one per teammate, each spawned over real stdio. Both sync from a common base, both go offline — by pointing the remote at a path that does not exist, which is real rather than simulated — each records a decision, and both come back. Ana syncs first, so Ben must merge rather than clobber. Every input arrives from a real tool call, and every assertion is a property: count, uniqueness, parseability, convergence. There is nothing to hard-code and nothing to drift.

The ceiling: five things CI cannot prove

Named plainly. The honesty of this whole document rests on this list, so nothing here is softened, and none of it is counted as closed.

The precise claim a green pipeline makes

Every deterministic surface of this plugin behaves correctly through its real interfaces.

That is the whole claim. It does not extend to whether the model chooses to call anything, nor to whether the harness sends the payloads the fixtures assume. Those two are tracked as named risks with a re-check cadence, and they stay open.

What "done" means for the whole rebuild

  1. Every unit merged, or retired by a recorded decision naming the reason.
  2. Every defect in the register closed by a named unit, or explicitly deferred with an owner. None silently dropped.
  3. A refusal from any tool names its field, an accepted example, and whether a retry can succeed.
  4. No call leaves partial durable state; concurrent calls never collide on an identifier.
  5. Stored text cannot forge server-authored instruction on any surface.
  6. Two people working offline and merging lose nothing.
  7. Ships 1.0.0 with both manifests in agreement.

Items 3, 4, 5 and 7 are the four criteria the previous attempt left open — of its seven, one was met. Item 6 is new, and is what the team-sync decision made first-class.

Section 8Glossary

MCP
Model Context Protocol. The published protocol by which a client program offers a language model access to a small server's tools (callable actions) and resources (readable addresses).
stdio
Standard input and standard output — the plain byte pipes a parent process uses to talk to a child. Logbook's server is spawned as a child and speaks the protocol over them, which is why a single stray printed character corrupts the channel.
hook
A small program the client runs when a defined event occurs. It reads one JSON event on standard input and replies on standard output; exit code 2 blocks on the events that support blocking, and any other non-zero code does not block — so a mistyped script path silently disables a policy gate.
skill
A Markdown file of instructions the model can follow. In the rebuild, skills orchestrate and hold no rules.
thread
One line of work, with a goal, completion criteria and a running summary. The unit Logbook remembers.
spine
The fixed-field running summary carried on a thread: active goal, next step, what the last session did, open risks, key decisions, and what is out of scope.
worktree
A checked-out copy of a git repository on disk. Useful for a developer; unsuitable as a database, because it has no concurrency model.
plumbing
Git's low-level command set, which manipulates objects and refs directly, beneath everyday commands like commit and checkout.
ref
A named pointer to a commit. Branches are refs under refs/heads/; the ledger's ref deliberately lives outside that namespace, so garbage collection still protects it but it never appears as a branch and cannot be checked out by accident.
orphan ref
A ref whose commit history is unrelated to the project's own branches — a parallel history sharing the same object store.
compare-and-swap
Moving a pointer only if it still holds the value you read, and failing loudly if it does not. It is what stops two processes silently overwriting each other. Today the ledger's ref move passes no old value at four call sites.
fsync
An instruction to the operating system to flush buffered data to durable storage. Flushing the directory after a rename is the step that makes the rename itself survive a crash.
ULID
A sortable, time-prefixed identifier that two machines can generate independently without coordinating and without colliding — which is what makes offline merge possible.
mutation testing
Deliberately introducing small changes into production code to check that some test turns red. It measures whether the assertions actually assert. Never gated at 100%, because equivalent mutants are undecidable.
census (as a check)
A check that enumerates every member of a closed set and halts on anything it cannot classify — as opposed to sampling. Used here for schema property descriptions and for escaping sites in the renderers.
structured output
A declared schema for a tool's result. The protocol validates the result against it, which is the one place correctness is enforced for free. Zero tools declare one today.
idempotent
Safe to call more than once with the same effect as calling it once. Resuming a thread twice is not an error.
