# Deferred Cap and Budget Items Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the ten ruled deferred cap and budget items: remove the record size caps and the named length caps, quarantine unreadable records, take five unknown keys before escaping them, escape artifacts at write, and give every risk a declared anchor, duplicate matching and next-step filtering in the briefing.

**Architecture:** Logbook stops refusing writes for their size or length, except where a limit is not a chosen number. Every removed cap is removed from three places together: the constant in `src/schema/caps.ts`, the tool input schema that publishes it, and the stored-record schema that re-checks it on read. The briefing keeps its render budget and floors unchanged; floors that were derived from a removed cap keep their numeric value as a named literal. Risks gain a required `criterion_id` that is either a criterion id or `null` for the whole thread, and the spine gains `next_step_criterion_id`, which the briefing uses to show only the risks that bear on the next step.

**Tech Stack:** TypeScript run directly by Node via type stripping (no build step), Zod 4 schemas, `node:test`, git-native storage on a dedicated ref, MCP server over `@modelcontextprotocol/sdk`.

**Spec:** `docs/specs/2026-09-11-deferred-cap-items.md`

**Thread:** `01M2GKR3E4G5QN5B7N5A7GAVGB` (deferred-cap-items-implementation)

**Why Unit 8 follows Unit 7.** Escaping an artifact label at write can lengthen it. While `ARTIFACT_LABEL_MAX` still exists on the stored schema, a label with escapable characters near 200 characters would fail stored-shape validation. Unit 7 removes that cap first. This supersedes the spec's "Suggested order", which listed item 2 with no dependency.

## Unit 1 — An unreadable record is quarantined instead of failing every read

**What ships.** A record file that cannot be read, for any reason other than not existing, is quarantined with the error code. Every other record in the project stays readable.

**The symptom being fixed.** One unreadable file under the threads directory makes `list_threads`, the roster and sync fail for every thread in the project, because `readRecordFile` rethrows every error except `ENOENT` and its callers loop with no per-file protection.

**Why merging this alone is safe.** `readRecordFile` already returns a quarantined slot for malformed JSON and schema failures, and every caller already handles quarantined slots. This change adds one more path into that existing outcome.

```ts
import path from 'node:path'
import * as caps from '../schema/caps.ts'
import { ULID_PATTERN } from '../schema/ids.ts'
import { SessionRecord, type Ulid } from '../schema/session.ts'
import { errnoCode } from '../store/detail.ts'
import { readRecordFile } from '../store/read-path.ts'
import { PARK_THREAD_ACTOR } from './session-log.ts'

const JSON_EXTENSION = '.json'

const sessionsDirFor = (recordsDir: string, threadId: Ulid): string => path.join(recordsDir, 'sessions', threadId)

const stemOf = (fileName: string): string => fileName.slice(0, -JSON_EXTENSION.length)

export const unparkedSessionEntriesSaturateBound = (recordsDir: string, threadId: Ulid): boolean => {
  let entries: string[]
  try {
    entries = readdirSync(sessionsDirFor(recordsDir, threadId), { withFileTypes: true })
      .filter((entry) => entry.isFile() && entry.name.endsWith(JSON_EXTENSION))
      .map((entry) => entry.name)
  } catch (error) {
    if (errnoCode(error) === 'ENOENT') return false
    throw error
  }

  const orderedNewestFirst = entries.filter((name) => ULID_PATTERN.test(stemOf(name))).sort().reverse()

  let count = 0
  let scanned = 0
  for (const name of orderedNewestFirst) {
    if (scanned >= caps.SESSION_UNPARKED_ENTRIES_MAX) break
    scanned += 1
    const filePath = path.join(sessionsDirFor(recordsDir, threadId), name)
    const slot = readRecordFile(filePath, SessionRecord)
    if (slot === null) continue
    if (slot.quarantined) {
      count += 1
      continue
    }
    if (slot.record.actor === PARK_THREAD_ACTOR) return false
    count += 1
  }
  return count >= caps.SESSION_UNPARKED_ENTRIES_MAX
}
```

## Unit 2 — A refusal takes five unknown keys before escaping them

**What ships.** When a tool call carries unknown argument names, the refusal escapes and clips only the five names it shows. The refusal text is byte-for-byte unchanged.

**The waste being removed.** `renderUnrecognizedKeysField` at `src/schema/refusal.ts:38` escapes and clips every unknown key, then keeps five. A call with thousands of unknown names does thousands of escape passes, each able to expand its input six-fold, to print five. The path is reached only by a tool call's own arguments: tool inputs are strict objects (`src/server/register.ts:66-69`), and stored records strip unknown keys, so a synced record never reaches it.

**This is not a behaviour change**, so there is no red-before test. The output is identical by construction: the five keys shown are the same five either way, and the remainder count comes from the full key list in both versions. A characterization test pins the exact output and passes both before and after. The commit type is `perf`.

**Why merging this alone is safe.** One pure function changes, and its exact output is pinned before the edit.

## Unit 4 — The header and spine text caps are removed

**What ships.** A thread title, `blocked_by`, active goal, next step, last session and landed value of any length is accepted by `open_thread`, `update_thread` and `park_thread`, stored, and read back. The six constants `THREAD_TITLE_MAX`, `THREAD_BLOCKED_BY_MAX`, `SPINE_ACTIVE_GOAL_MAX`, `SPINE_NEXT_STEP_MAX`, `SPINE_LAST_SESSION_MAX` and `SPINE_LANDED_MAX` are deleted from the tool input schemas, the after-escaping refusals, the spine contribution check, and the stored thread schema. In the briefing, the next step renders whole; the other five header fields keep today's 500-grapheme clip through `FORMER_HEADER_FIELD_WRITE_MAX`. The tool descriptions for the next step, active goal and last session now say what each field is for.

**The symptom being fixed.** A next step, goal or title one character past its cap was refused, and a value within the cap was refused when escaping pushed it over, so the writer had to cut content to get it stored.

**Why merging this alone is safe.** Removing a refusal cannot break a caller that already succeeded. The render budget and every clip other than the next step's are unchanged.

**What ships.** `update_thread` requires every entry in `risks_add` to carry `criterion_id`, either the id of a completion criterion on the thread or `null`, which means the risk bears on the whole thread. ## Unit 11 — The next step names its criterion and the briefing shows only the risks that bear on it

**What ships.** `update_thread` and `park_thread` accept `next_step_criterion_id` in the same call as `next_step`. It names the open completion criterion the next step advances and is stored as `spine.next_step_criterion_id`. Every `next_step` write replaces it: a `next_step` sent without it stores none. ## Unit 13 — Release 10.0.0 and reinstall the plugin

**What ships.** The version moves from 9.1.0 to 10.0.0 in `.claude-plugin/plugin.json`, `package.json` and the two version fields of `package-lock.json`, and nothing else. After it merges, the installed plugin is updated so the running logbook is the one Units 1 to 12 built.

**Why 10.0.0 and not 9.2.0.** OR44 (`docs/plans/2026-08-28-continuity-goal-model/ORCHESTRATOR-RULINGS.md`) sets the release from the units it carries: any unit that proved a break in the published contract takes a major. Unit 9 is one. A `risks_add` entry with no `criterion_id` succeeded on 9.1.0 and is refused on 10.0.0, and `update_thread.refuses-a-risk-that-declares-no-anchor` proves it against a spawned server. Decision `01M2GXXZNG24TV1X2QX33EPAGX` records this; it corrects the 9.2.0 that earlier drafts of this plan named.

**What changes for the sessions that use logbook.** After the reinstall and a session restart, every `update_thread` call that adds a risk sends `criterion_id` (a criterion id, or `null` for the whole thread). A repeated risk returns the live one in `risks_already_present`. `next_step_criterion_id` narrows the briefing's risks, and the `debrief` skill sends it.

**Why merging this alone is safe.** The two manifests change together, and `cutover.manifests-agree` fails when they disagree with each other or with the version the server reports.
